Each entry in `Issuers` is one source of tokens. A token is accepted when its issuer, audience and claims match an entry. Every entry accepts these settings:

| Setting          | What it does |
| ---------------- | ------------ |
| `Name`           | A name for log messages and for `[RequireOidcToken(...)]`. Defaults to the preset name or the issuer URL. |
| `Preset`         | `Vercel`, `GitHubActions`, `GitLab`, `Azure`, or `Custom` (the default). |
| `Audience`       | The `aud` the token must carry, which names the service the token was made for. |
| `RequiredClaims` | Claims the token must carry, each with its allowed values. Added to the preset's own rules. |
| `AllowPreview`   | Whether the token also unlocks draft content, as the API key does. Defaults to `true`. |
| `MetadataAddress`| Where the issuer publishes its keys. Defaults to `{issuer}/.well-known/openid-configuration`. |

## Vercel

See Vercel's [OIDC federation docs](https://vercel.com/docs/oidc) for how tokens are issued and what they contain.

```json
{ "Preset": "Vercel", "Team": "acme" }
```

- `Team` is your team slug, and the only required setting. Tokens from any other team are refused.
- `Projects` limits access to some of the team's projects, by name or id, such as `["acme-web", "prj_123"]`. Leave it out to accept every project in the team.
- `Environments` defaults to `production` and `preview`. To let local machines in as well, add `development`: `"Environments": ["production", "preview", "development"]`. The `development` token is the one `vercel env pull` writes for local work, and anyone on the team can pull it.
- `IssuerMode` is `Team` (the default) or `Global`, matching your team's OIDC settings on Vercel.
- `Audience` defaults to `https://vercel.com/{team}`, which is what `getVercelOidcToken()` returns.
- Builds get a token too, through `VERCEL_OIDC_TOKEN`, so static generation works.

## GitHub Actions

See GitHub's [OpenID Connect docs](https://docs.github.com/en/actions/concepts/security/openid-connect) for how workflows request tokens and what they contain.

```json
{ "Preset": "GitHubActions", "Owner": "acme" }
```

`Owner` is your GitHub organization, or a user, written as GitHub writes it. It is the only required setting, and tokens from any other owner are refused. On its own it accepts every repository the owner has. To narrow it down, add any of these filters:

- `Repositories`, as `owner/repo`, such as `["acme/site"]`.
- `Refs`, such as `["refs/heads/main"]`.
- `Environments`, the GitHub deployment environments allowed in.

Request the token in a job with `permissions: id-token: write`:

```js
const token = await core.getIDToken();
```

The token's audience says which service it was made for. Without an argument, GitHub uses `https://github.com/{owner}`, which is also this preset's default. With that default, a token your workflows send to another service that accepts GitHub's default audience would also work on your CMS. To keep them apart, pick your own audience: set it as `Audience`, such as `"https://cms.example.com"`, and pass the same value to `core.getIDToken('https://cms.example.com')`.

## GitLab

See GitLab's [ID token docs](https://docs.gitlab.com/ci/secrets/id_token_authentication/) for how jobs request tokens and what they contain.

```json
{ "Preset": "GitLab", "Namespace": "acme", "Audience": "https://cms.example.com" }
```

`Namespace` is the full path of your group, or a user, such as `acme` or `acme/web`. It accepts every project in the group and its subgroups, and tokens from anywhere else are refused. `Audience` is required, because GitLab has no default: pick a value for your CMS and declare the same one in the job. To narrow it down, add any of these filters:

- `Projects`, as full paths, such as `["acme/web/site"]`.
- `Refs`, such as `["refs/heads/main"]`.
- `Environments`, the GitLab environments allowed in.

Declare the token in the job, and send `$UMBRACO_TOKEN` in the header:

```yaml
build:
  id_tokens:
    UMBRACO_TOKEN:
      aud: https://cms.example.com
```

For a self-managed instance, set `Host` to its address, such as `"https://gitlab.example.com"`.

## Azure

See Microsoft's [managed identity docs](https://learn.microsoft.com/en-us/entra/identity/managed-identities-azure-resources/overview) for which Azure services have one and how they get tokens.

```json
{
  "Preset": "Azure",
  "TenantId": "3f2b8c1d-6e4a-4b7f-9d2c-8a1e5f3b7c90",
  "Audience": "6e74172b-be56-4843-9ff4-e66a39bb12e3",
  "PrincipalIds": ["e9b1f3a0-4c2d-4f7e-9a51-3b8c6d2e1f04"]
}
```

Entra ID only issues tokens for apps it knows, so the site needs an app registration of its own:

1. Under App registrations in Entra ID, register an app for the site, such as `Umbraco CMS`. It needs no redirect URI, secret or API permissions. Its Directory (tenant) ID is the `TenantId`, and its Application (client) ID is the `Audience`.
2. Turn on a managed identity for each workload, such as an App Service, Function App, Container App or virtual machine, or set up workload identity on AKS. Its Object (principal) ID goes in `PrincipalIds`.

All three settings are required. By default, any app or managed identity in the tenant can get a token for your app registration, so `PrincipalIds` is what keeps the rest of the tenant out. To let in a workload that signs in as an app registration instead, use the Object ID shown for it under Enterprise applications, not the one under App registrations.

Request the token with the app's client ID as the scope. With `@azure/identity`:

```ts
import { ManagedIdentityCredential } from '@azure/identity';

const credential = new ManagedIdentityCredential();
const { token } = await credential.getToken('6e74172b-be56-4843-9ff4-e66a39bb12e3/.default');
```

For a user-assigned identity, pass its client ID: `new ManagedIdentityCredential({ clientId })`.

Entra ID issues v1.0 or v2.0 tokens, depending on the app registration's `requestedAccessTokenVersion`, and the preset accepts both. A v2.0 token always carries the client ID as its audience. A v1.0 token carries whatever the workload asked for, so if your workloads ask for an Application ID URI such as `api://umbraco-cms` instead, set that as `Audience`. It then works with v1.0 tokens only.

Azure Government and the other national clouds sign in on another host. Set them up as a [custom issuer](#any-other-issuer).

## Any other issuer

`Issuer`, `Audience` and at least one required claim are needed. Without a claim, any workload the issuer serves could get in. With Google, for example, that would be anyone with a Google account. Each required claim must match a top-level string claim in the token, including its case.

:::tip
Decode a real token from your workload, for example with [jwt.io](https://jwt.io), before you write the entry: it shows the exact `iss`, `aud` and claims to match.
:::

### Google Cloud

Request an [ID token](https://docs.cloud.google.com/docs/authentication/get-id-token) from the metadata server with your audience, and require the service account's email:

```json
{
  "Name": "renderer",
  "Issuer": "https://accounts.google.com",
  "Audience": "https://cms.example.com",
  "RequiredClaims": { "email": ["renderer@acme.iam.gserviceaccount.com"] }
}
```

### AWS

Request a token with [`GetWebIdentityToken`](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_roles_providers_outbound.html) after enabling outbound identity federation on the account. The issuer is specific to your account, and `sub` is the [ARN of the role](https://docs.aws.amazon.com/IAM/latest/UserGuide/id_roles_providers_outbound_token_claims.html) that asked for the token:

```json
{
  "Name": "lambda-renderer",
  "Issuer": "https://abc123-def456-ghi789-jkl012.tokens.sts.global.api.aws",
  "Audience": "https://cms.example.com",
  "RequiredClaims": { "sub": ["arn:aws:iam::123456789012:role/Renderer"] }
}
```
